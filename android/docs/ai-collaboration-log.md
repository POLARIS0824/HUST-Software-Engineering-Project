## 2. 逐轮协作全过程记录 (Rounds 1 ~ 12)

### 2.1 Round 1：选题定位与移动端原生方向探索

#### 【输入 Prompt】
> 这是选题：个人 Markdown 笔记与知识管理工具。  
> 面向学生与知识工作者的本地优先笔记工具，支持 Markdown 编辑、标签与全文检索、双链引用、导出。移动端需要，并且是原生 Android 开发。  
> 我的目的不只是做完课程实验，还要通过这个项目提升 Android 原生开发工程能力以及作为未来 Android 实习求职作品。  
> 请先帮我深入分析这个选题的业务空间与大的技术执行方向。

#### 【AI 主要建议】
1. 建议将产品定位于“Local-first 原生 Android Markdown 个人知识库”。
2. 架构应涵盖：Markdown 源码编辑、正文 Tag 体系、全文检索（FTS）、WikiLink/Backlink 双向网络、本地导出与冷备。
3. 提示在移动端切忌直接照搬桌面端 Obsidian 的全量插件体系，建议将第三方插件、多人实时协同明确排除在 V1 之外。
4. 建议优先考虑通过 WorkManager 配合 WebDAV 实现跨端同步。

#### 【人工审阅与处理决策】
* **采纳**：Local-first 定位、Tag 知识组织、WikiLink/Backlink 网状关联；排除插件与多人协同（复杂度过高且偏离个人单机沉浸记录定位）。
* **修改**：对 WebDAV 同步提出降级。移动端首发应聚焦于“本地数据绝对自主可控（Local-first）”，若初期引入网络同步机制，容易掩盖本地文件读写与生命周期处理的底层缺陷。
* **决策结论**：确立系统的第一核心架构基准：**Android-first + Local-first + Markdown-first**。

### 2.2 Round 2：原生 WYSIWYG 误区澄清与可行性辨析

#### 【输入 Prompt】
> “所见即所得”在手机端体验很好，直接像传统富文本编辑器那样在 Compose 里做一个所见即所得的 Markdown 编辑器为什么很难？是否可以直接照搬 Obsidian 的移动端实现？

#### 【AI 主要建议】
1. 深度技术辨析：指出“传统富文本 WYSIWYG（如 Word/Notion）”、“Obsidian Live Preview（即时渲染）”与“纯文本源码编辑器”三者底层的本质差异。
2. 论证原生 Jetpack Compose 从零实现 Live Preview 的极高门槛：需要自主构建 Markdown AST 解析器、行内 Decoration 动态注入、Selection/Cursor 虚拟偏移映射、VisualTransformation 以及复杂的中文 IME 复合文本状态处理。
3. 提示：Obsidian 移动端并非纯原生，而是基于 Capacitor / Electron + CodeMirror 6 的 Web 技术栈封装。

#### 【人工审阅与处理决策】
* **深入调研**：人工检索 GitHub 上现有的 Android Compose Markdown 编辑器开源项目，证实目前社区尚无完全成熟的原生即时渲染 Compose 库，大部分自研实现均在中文长文本输入与光标定位上存在严重 Bug。
* **否决初始冲动**：坚决否决“在课程时间内自研纯原生 Compose 即时渲染编辑器”的激进想法。
* **架构重构**：将技术方案调整为“Android 原生主体（Compose 负责页面路由、文件管理、检索列表）+ WebView 编辑内核”的混合架构，兼顾开发可行性与 Android 工程能力训练。

### 2.3 Round 3：Native-only 与 Native-first 的权衡取舍

#### 【输入 Prompt】
> 如果采用 WebView 来支撑编辑器，我的项目目标是提升 Android 原生实习竞争力，这是否会导致项目变成一个简陋的套壳 Web App？我该如何在架构上进行平衡？

#### 【AI 主要建议】
1. 提出关键架构理念：**Native-first，而非 Native-only**。
2. 明确职责切分边界：
   * 原生 Android (Jetpack Compose / ViewModel / Room / Coroutines) 统领 80% 的系统功能：应用导航生命周期、多主题管理、本地文件 I/O 调度、Room FTS5 搜索引擎、双链图谱索引、SAF 框架集成。
   * WebView 严格降级为局部的“文本渲染与编辑容器”，不持有业务逻辑。
3. 建议定义抽象接口 `EditorEngine`，通过契约接口（`setContent`, `getContent`, `onLinkClick`）将 Web 编辑器与 Android 领域层解耦。

#### 【人工审阅与处理决策】
* **完全采纳**：该方案既守住了 Android 原生工程的深度（涉及跨进程生命周期、WebViewAssetLoader 安全沙箱、原生与 JS 双向消息总线等现代混合架构核心考点），又确保了高品质的即时渲染体验。

### 2.4 Round 4：WYSIWYG 概念向 Instant Rendering 的精准修正

#### 【输入 Prompt】
> 经过进一步查阅 Typora 和 Markor，我发现我真正需要的并不是把 Markdown 标记永久抹去的 Word 式“富文本”，而是像 Typora 那样平时排版好看、光标移上去又能修改源码的体验。这种需求在软件工程上该如何准确定义？

#### 【AI 主要建议】
1. 术语纠偏：明确指出该交互范式在业内标准术语为 **Instant Rendering（即时渲染，简称 IR）** 或 **Live Preview**，绝非传统 WYSIWYG。
2. 候选 Web 编辑器对比：
   * *CodeMirror 6*：底层基建成熟，但构建 IR 需自研大量 ViewPlugin 与 Decoration，工程量极大；
   * *Milkdown*：基于 ProseMirror，偏向结构化富文本，对 Markdown 源码格式具有强格式化重写倾向；
   * *Vditor*：开箱即用支持完整的 IR（Instant Rendering）模式，天然契合 CommonMark 与 GFM。

#### 【人工审阅与处理决策】
* **关键修正**：在需求定义中，**正式将所有“WYSIWYG”表述彻底更正为“Instant Rendering”**。
* **技术决策**：选定 Vditor IR 作为首要技术候选，但将其显式标注为“实现技术候选”，需求正文只对 Instant Rendering 行为提出约束。

### 2.5 Round 5：Tag 系统与单一事实源分层设计

#### 【输入 Prompt】
> 对于 Tag 标签功能，我最初的想法是在 Room 数据库里建一个 tags 表，同时用户在 Markdown 正文里写 `#tag`。但如果用户在外部文本编辑器里改了标签，数据库怎么同步？到底以谁为准？

#### 【AI 主要建议】
1. 指出双存储架构的致命隐患：若 Markdown 正文与 Room 数据库同时被视为“事实源（Source of Truth）”，必然在离线、外部编辑或备份还原时引发双写冲突（Split-brain 脑裂）。
2. 架构定性：必须严格贯彻 Local-first 准则，定义 **Markdown 纯文本为唯一事实源**，Room 数据库中的 Tag 表纯属**派生缓存索引（Derived Index）**。
3. 提取机制：保存文件时由后台协程异步扫描正文，增量更新 Room；当数据库损坏或不一致时，无条件以 Markdown 正文解析结果进行覆盖自愈。

#### 【人工审阅与处理决策】
* **完全采纳并升华为业务规则**：确立业务规则 `BR-01`（Markdown 为事实源）与 `BR-02`（索引全属派生数据）。

### 2.6 Round 6：网状知识拓扑（WikiLink 与 Backlink）规则设计

#### 【输入 Prompt】
> 知识管理工具的核心差异在于双链。在 Android 移动端，`[[笔记名称]]` 的语法应该如何工作？如果引用的笔记被删除了，或者用户输入了一个还不存在的链接名称，系统应该怎么处理才符合软工规范？

#### 【AI 主要建议】
1. 语法选型：采用被广泛接受的双中括号语法 `[[笔记名称]]` 与别名语法 `[[笔记名称|显示别名]]`。
2. 针对未解析链接（死链）的处理策略：
   * 严禁静默崩溃；
   * 允许悬空链接（Dangling Link）合法存在，并渲染为特殊的未解析状态（如虚线高亮）；
   * 用户点击未解析链接时，提供“快速创建同名新笔记”的捷径弹窗。
3. 反向引用（Backlink）回路：在数据库中维护笔记间的有向图关系。A 引用 B，则在 B 底部展示 A 的反向引用卡片。若 A 中的链接被删除，后台自动消除关联，严禁修改 A 之外的其他文件。

#### 【人工审阅与处理决策】
* **采纳并完善**：确立业务规则 `BR-06` 与 `BR-07`，并将“未解析链接点击引导创建”归入中优先级功能，为非线性知识卡片构建提供理论支撑。

### 2.7 Round 7：11 款代表性竞品横向深度评测与差异化收敛

#### 【输入 Prompt】
> 我人工筛选并查阅了 11 款在移动端和 Markdown 领域具有代表性的产品：  
> Obsidian、Typora、Markor、Joplin、Markleaf、Nouto、Kori、MarkReader、SoloMD、JotterPad、HelixNotes。  
> 请针对这 11 款产品的特性进行深度横向对比，帮助我重新审视项目的差异化定位，防止伪需求堆砌。

#### 【AI 主要结论与竞品矩阵】
AI 协助建立了覆盖全部 11 款竞品的横向能力矩阵，发现：
* **Markor / Joplin**：本地能力扎实，但 Markor 缺少 IR 即时渲染（源码体验重），Joplin 界面偏向传统树状表单且移动端笨重；
* **Obsidian**：功能极其强大，但移动端冷启动慢（~3-5s），移动端交互为桌面 Web 移植版，且对新手配置极为复杂；
* **Markleaf**：与本项目设想高度接近（Android 原生 + 本地优先 + 双链），证明该产品组合是极为精准的刚需；
* **Nouto / MarkReader / Kori**：展示了现代 Material 3、Dynamic Color 动态取色在阅读类工具上的极佳质感；
* **SoloMD / Kori / Joplin**：已集成或开始试验 AI 总结、对话与云端同步；
* **HelixNotes / JotterPad**：面向结构化大纲或小说创作，格式存在私有扩展锁定倾向。

#### 【人工审阅与定位收敛】
* **关键战略反思**：最初曾设想“通过加入轻量级 AI 对话来形成差异化”，但竞品调研彻底击碎了这一假设——在本地基础设施（文本输入、双链穿梭、秒级检索）尚未夯实前，盲目堆砌调用云端 LLM 的 AI 功能不仅同质化严重，更会彻底破坏 Local-first 纯净本地体验。
* **最终差异化定位**：**聚焦于“Android 原生极速响应 + 零门槛即开即用 + Material 3 现代触控 + 开放纯文本 Local-first”**。将 AI 功能果断排除在 V1 之外。

### 2.9 Round 9：功能需求域拆解与来源依据绑定

#### 【输入 Prompt】
> 将上述 12 项用户需求细化下沉为具体的功能需求（FR）。请按业务领域（笔记管理、编辑器、Tag、FTS、WikiLink、数据管理、UI）分域拆解，并为每条需求标注优先级与技术实现依据。

#### 【AI 主要建议】
AI 输出了初步的 FR 表格，但存在以下缺陷：
1. 优先级划分过于扁平（大量标记为“高”，缺少梯次）；
2. 部分条目存在跨域重复（如笔记 CRUD 离线与数据管理离线重复描述）；
3. 缺少明确的需求来源追踪列。

#### 【人工审阅与重构优化】
* **实施足额三级优先级**：强制推行 MoSCoW 原则（高 / 中 / 低），对次要功能（如复杂公式高亮、动态主题色适配、字数统计）果断降级为中/低优先级，并为每条中低优先级项详注降级理由。
* **去重合并**：将原重复的离线描述彻底合并为规范的架构声明。
* **全量补充来源列**：为全部需求表格新增「来源 / 依据」列，精确关联至具体使用场景（SCN）、业务规则（BR）或竞品调研结论。

### 2.10 Round 10：非功能需求定量化与消除二义性

#### 【输入 Prompt】
> 检查前一轮的非功能需求（NFR）。目前很多表述包含“软件应流畅”、“正常连续编辑”、“不得导致异常”等主观词，无法作为客观测试依据。请配合我将其全部改写为可测量、可判定的量化工程阈值。

#### 【AI 主要建议】
AI 提出了一系列性能与可靠性指标，但出现**口径自相矛盾**的问题：在性能小节提出了“≤50 KB 普通笔记”，但在讨论字符吞吐时又提到了“<1 万字”，且可靠性、易用性条目未分配独立编号。

#### 【人工审阅与彻底消解】
* **统一指标口径**：将全套文档中的“普通笔记”标准严格统一为：**「文件大小 ≤ 50 KB 且字符数 < 10,000 字」**，彻底消除跨章节口径冲突。
* **消解所有主观性词汇**：
  * “正常连续编辑” $\rightarrow$ 量化为：50,000 字符长文本下，以 5 字符/秒连续输入，UI 输入时延 P95 $\le 50\text{ ms}$，帧率 $\ge 55\text{ FPS}$，无 ANR；
  * “有效撤销机制” $\rightarrow$ 量化为：内存保留 100 步撤销历史，删除操作提供 5 秒 Snackbar 即时撤回与本地回收站 30 天防灾缓冲；
  * “主要操作目标不超过 2 次” $\rightarrow$ 量化为：从主页到新建、搜索、查双链手势点击步数严格 $\le 2$ 步。
* **全面编号化**：构建 `NFR-PERF`（性能）、`NFR-REL`（可靠性）、`NFR-USE`（易用性）、`NFR-PORT`（可移植性）、`NFR-SEC`（安全）、`NFR-ACC`（无障碍）、`NFR-MAINT`（可维护性）七大编号体系。

### 2.11 Round 11：验收标准体系构建（全面推行 Given/When/Then）

#### 【输入 Prompt】
> 目前验收标准（AC）只有寥寥 8 个概括性条目，许多已编号的 FR（如笔记重命名、删除撤销、中文 IME 混输、同名冲突导入、TalkBack 无障碍）没有对应测试用例。请采用工业级 BDD（Given/When/Then）范式，为各领域编写严密的验收标准。

#### 【AI 主要建议】
AI 给出了部分 BDD 语法的示例，但初期覆盖率不足，未覆盖断电故障模拟与复杂分词场景。

#### 【人工审阅与全面扩充】
* **重构验收体系**：人工主导扩充并编写了完整的验收标准集（涵盖 AC-NOTE-01~03、AC-EDIT-01~03、AC-TAG-01~02、AC-SEARCH-01~02、AC-LINK-01~02、AC-DATA-01~03、AC-UI-01~02、AC-PERF-01~03）。
* **格式严格统一**：确保每一条用例均显式包含**测试前置条件（Given）、用户操作步骤（When）与量化客观判定标准（Then）**，与协作日志中所声称的 BDD 交付标准保持 100% 绝对一致。

### 2.12 Round 12：边界控制、风险识别与技术 Spike 制定

#### 【输入 Prompt】
> 我们即将进入开发阶段，请协助评估本项目面临的最大技术风险与不确定性。如何设计一组针对性 Spike 实验来提前排雷？

#### 【AI 主要建议】
梳理出 7 项潜在技术风险：Vditor 中文 IME 兼容性、WebView 生命周期与进程被杀重建、Markdown AST Round-trip 转换损毁、WikiLink 语法在 Webview 扩展可行性、SQLite FTS5 中文分词效率、自动保存并发文件竞争损坏、Native Bridge 安全边界。

#### 【人工审阅与处理决策】
* **采纳并建立 Spike 计划**：形成开发前必须完成的 **Spike 1 ~ Spike 7** 攻关路线图。

## 5. 人工对 AI 输出做出的六大关键工程修正

回顾整个需求分析迭代过程，最具工程价值的人工纠偏体现在以下六个方面：

### 修正一：概念定性纠偏 —— WYSIWYG $\rightarrow$ Instant Rendering
AI 初期频繁使用“富文本所见即所得（WYSIWYG）”这一宽泛词汇，容易误导开发团队走向 Word/HTML 式的富文本路线。人工查阅 Typora、Obsidian 架构后，敏锐指出用户的核心诉求是“保留纯文本 Markdown 语法掌控力，同时消除视觉排版干扰”，从而果断将需求基准收敛为 **Instant Rendering**。

### 修正二：技术路线理性回归 —— Native-only $\rightarrow$ Native-first
针对自研 Compose 编辑器的执念，深入开源社区调研，清醒地认识到在有限时间内无法独立攻克中文 IME 组合输入法与光标映射的极端复杂性。决定采取务实的 **Native-first** 策略：由 原生 Compose 统领全局架构，局部引入成熟 Web 容器支撑文本渲染，既保障了工程落地，又避免了项目失控。

### 修正三：解耦产品需求与具体技术库 —— Vditor 是手段而非需求
AI 在规格化编写时曾一度将“系统必须基于 Vditor 渲染”写入需求条目。人工审阅时坚决予以剔除，明确指出：**系统的法定需求是支持 CommonMark/GFM 规范的即时渲染**。Vditor 仅是当前最具性价比的技术候选方案；一旦后续 Spike 验证失败，团队随时可以在不变更需求基线的前提下平滑替换实现。

### 修正四：消除双写脑裂隐患 —— 严格确立单一事实源 (Source of Truth)
AI 初版建议在数据库与文件系统中同时持久化 Tag 关系。人工从数据一致性角度出发，果断予以否决，建立铁律：**本地 `.md` 文件是全系统唯一事实源，数据库中任何数据皆属随时可全量自愈的派生缓存**，从根源上杜绝了多事实源引发的脑裂与数据丢失。

### 修正五：抵制功能膨胀，挤出 AI 噱头泡沫 —— 降级 AI 为远期探索
在头脑风暴阶段，AI 顺从用户想法罗列了大量关于 AI Chat、Agent Tool Calling 等时髦特性的设想。人工在完成 11 款竞品横向实测后发现，移动端笔记的核心短板绝非“没有 AI”，而是“文字输入不畅、多笔记检索慢、格式易被绑定”。毅然将 AI 剥离出 V1，集中精力构筑高可靠的纯本地离线核心。

### 修正六：端正工程严谨态度 —— 假定指标不得伪称已测事实
AI 初版生成的性能指标表格带有强烈的“已实现”暗示口吻。人工严格将其纠偏为“设计目标与技术假设（⚠️ 暂定）”，并在规格说明书中附上 7 项开发前必须履行的 Spike 计划，坚决杜绝“先画靶后射箭”的不实表述。

## 6. 协作总结与工程认知

通过本次系统化的人机协同需求工程实践，对人机协作下的软件工程方法论形成了更深刻的认知：

> **生成式 AI 的最佳生态位是“具备广博视野的初级架构顾问与秘书”，而非“具有最终裁决权的软件工程师”。**

AI 能够以极高的效率帮助开发者发散思维、罗列竞品维度、编写规格模板，并提醒潜在的风险盲点。然而，面对真实复杂的工程环境，**对核心业务价值的取舍、对技术可行性边界的警惕、对单一事实源等底层软件工程原则的坚守，以及对数据可移植性与无障碍包容性的承诺，必须始终牢牢掌握在人类工程师手中。** 唯有坚持“人工批判审阅、公开资料求证、实机代码验证”，才能将浮躁的 AI 雏形炼化为真正经得起推敲的高水准工程需求基线。
