# CodeMirror View + Compose research

Verdict: ISSUES in the old probe; PASS as a feasible second-round architecture proposal. No build, Android interaction, IME test, or implementation was performed. No first-round artifact was changed.

## Recommendation and data shape

Use CodeMirror 6 as a visible-source editor inside one local-assets WebView. Keep B's Compose layout, native toolbar, note list, and a separate native Read pane identical to the Kotlin candidate. Do not add instant rendering to this comparison. This gives the two candidates the same edit/read task and avoids paying for an incomplete Markdown live-preview implementation.

Shared owner: `NoteDocument(id, markdown)`, `EditorImplementation`, `Edit/Read`, and `DraftSnapshot(text, selection(anchor, head), revision)`. Keep selection in UTF-16 offsets with direction, validate both endpoints against the document, and restrict the prototype to one selection. Canonical in-memory draft ownership stays in the session. CodeMirror owns its active editing transaction state and private per-note undo history, then publishes ordered snapshots to that owner. Do not reconstruct its document from Compose on every recomposition.

The snapshot alone cannot restore undo. Keep the CodeMirror WebView mounted for the comparison session, cache one `EditorState` per note inside it, and switch with `setState` after the previous note's state has been captured. Keep it mounted while Read content overlays it or occupies the same body region. Explicitly suspend editing/focus in Read mode. If the WebView must be destroyed, history can instead be serialized with `historyField` and restored with the same extensions, but this is extra prototype work. No process-death guarantee follows from either choice. Official [state/history reference](https://codemirror.net/docs/ref/#commands.historyField) and [system guide](https://codemirror.net/docs/guide/) describe these separate responsibilities.

## Existing probe deficiencies

1. `markers()` matches only ATX heading prefixes and `**bold**` per line. It also matches inside fenced code and ignores escapes, nested syntax, reference links, images, lists, tables, math, HTML and WikiLinks. Focused-line hiding does not handle selection spanning several lines. It scans the whole document on every selection, focus and content change. This is a heading/bold decoration sketch, not full IR.
2. The fidelity loop at lines 50–59 replaces the live setup with `extensions:[history()]`. Its append/undo evidence therefore tests source state and history, not Markdown parsing, decorations, Android typing, toolbar commands or native navigation. The final replacement at line 64 also omits history, the listener and decorations. Do not reuse that final editor for behavior verification.
3. Source-only storage avoids HTML serialization losses but does not prove byte fidelity for all input. Default line splitting and `doc.toString()` can normalize CRLF to LF. Existing corpus uses LF. For this round declare LF-only fixtures, or preserve line-ending policy explicitly with `EditorState.lineSeparator` plus `state.sliceDoc()`. Mixed original line endings require a more deliberate representation and must remain outside any blanket byte-preservation claim. Test trailing newlines, tabs, emoji, combining text and unknown syntax.
4. LocalEditor checks Vditor's hash even for CM. [index.html](D:/Code/HUST-Software-Engineering-Project/prototypes/looma-research/android/app/src/main/assets/editor/index.html) loads Vditor CSS/JS alongside CM. A new CM-specific asset entry should load only its pinned bundle. Delete neither old entry nor old evidence.
5. Appassets origin and network blocking are useful retained boundaries. Missing `WEB_MESSAGE_LISTENER` support currently leaves editing without draft propagation. A new prototype must fail visibly or mark the candidate unavailable rather than silently appearing to save.

## Minimal ordered bridge and toolbar

Use one long-lived session identity and per-note activation generation. Every inbound snapshot has `{sessionId, noteId, generation, sequence, text, anchor, head, contentRevision, canUndo, canRedo}`. Kotlin validates note identity, active generation, message shape/size, UTF-16 bounds and increasing sequence. Sequence advances for selection-only updates too; content revision advances for text changes. Origin validation alone does not establish message freshness.

`ready` must precede `activate(snapshot)`. `activate` responds with an acknowledgement identifying the accepted note/generation/revision. A command envelope contains `{commandId, noteId, generation, expectedRevision, operation}`. Execute commands in JS against the current state and current selection, not Kotlin's potentially delayed copy. Publish the resulting snapshot plus command acknowledgement. On stale generation or revision, reject and return current state rather than applying offsets to another document. Theme updates are independent of source activation.

Native toolbar commands: Undo, Redo, Bold, Heading, Link, Edit/Read. Invoke public `undo`/`redo`; implement formatting as one transaction over `state.selection.main`, with explicit new selection and an isolated history event so one Undo removes one toolbar action. Link can initially insert literal Markdown around the current selection, with no modal URL workflow. Do not mutate content DOM or rebuild a state for formatting. The official [commands reference](https://codemirror.net/docs/ref/#commands.undo) and [selection guide](https://codemirror.net/examples/selection/) are the relevant API boundaries.

Before Edit→Read, list navigation or candidate switching, send a flush request, await a snapshot/ack, and only then change the active body. Reject late packets from the old generation. Serialize navigation requests with pending toolbar operations. Preserve the previous note's EditorState in the JS map. Avoid switching during active IME composition; finish/blur composition and await its final source snapshot first. Android may report composition even for cursor placement, so actual behavior must be observed rather than inferred from a flag. Official [EditorView composition reference](https://codemirror.net/docs/ref/#view.EditorView.compositionStarted).

Read mode consumes the acknowledged draft source and never writes rendered output back to it. Use the same native renderer for both candidates if possible, or explicitly disclose renderer differences as a confound. Unknown syntax must stay in the source even when reading renders it literally.

## B layout, Dynamic Color and Material Expressive

Keep B's structure, spacing, rounded note cards, typography and paper-like content layout. The old `Style.Paper` selects fixed [PaperPalette.kt](D:/Code/HUST-Software-Engineering-Project/prototypes/looma-research/android/app/src/main/kotlin/edu/hust/looma/prototype/PaperPalette.kt), not Android Dynamic Color. Derive a single Material color scheme in the new shared shell using Android dynamic light/dark palettes on API 31+, with an explicit fallback below 31. Pass resolved roles to CM CSS variables, including surface/container, onSurface/onSurfaceVariant, primary, outline, selection background/foreground and caret. Never feed independent hex palettes to the two bodies.

MaterialExpressiveTheme and expressive motion already exist in MainActivity; B and Expressive are not mutually exclusive choices. Keep expressive native controls and motion in the common shell while using B's composition. Theme changes must only reconfigure styling, never reset document/history/selection. CodeMirror's official [configuration example](https://codemirror.net/examples/config/) supports compartment reconfiguration. Its [decoration example](https://codemirror.net/examples/decoration/) is useful only if a later separate live-preview spike earns its cost.

## Packaging choice and minimal runtime alternative

Prefer two flavors with common Compose/session/reader code and a small same-signature editor composable supplied by each flavor's source set. Put WebKit dependency and CM assets exclusively in the CM flavor. Physically exclude the JS bundle and WebView integration from the native artifact, and inspect the APK to verify that claim. Android's WebView runtime is a system component, not an embeddable APK engine dependency to subtract from app size.

Minimal alternative: one APK, shared screen and an `EditorImplementation` enum. A `when` chooses CM or Kotlin editor in the same body; switching waits for the flush handshake and rehydrates the same source snapshot. This is faster to operate and compares interaction/layout well. It cannot prove the native APK has no WebView/JS assets, cannot fairly compare installed/download size, and shares process startup, caches and memory with the other route. Undo histories are engine-private; transfer source/selection but either reset history explicitly on engine switches or retain separate per-engine histories and clearly label that behavior. Do not imply history equivalence merely because the text matches.
